# The EG path

`CATEGORY=EG` is an emulated/downloaded game: a PSP ISO repackaged as a single
`EBOOT.PBP` under NPDRM, the form PSN titles and `sign_np` output take.

**This path is implemented.** `pspbuild build-eg` turns a UMD image into a
signed EG container:

```console
$ pspbuild build-eg game.iso --content-id UL0000-ULUS10380_00-0000000000000000
Title:               LEGO® Batman™: The Videogame
Content ID:          UL0000-ULUS10380_00-0000000000000000
Image size:          1136689152 bytes
Blocks:              34689 of 32768 bytes, stored uncompressed
DATA.PSAR:           1137799456 bytes
Wrote EBOOT.PBP (1138357792 bytes)
```

For that disc the result matches `sign_np`'s byte for byte in every section
offset and in total size; only the values the format requires to be random
differ. The format itself was checked against four genuine Sony Store archives,
not just against `sign_np` — see §1.

A container built this way **boots on a retail PSP Slim running official
firmware**, and the game runs. Corrupting one byte of its signature makes the
same console refuse it, so the firmware is demonstrably checking rather than
merely permitting — see [COMPATIBILITY.md §1.1](COMPATIBILITY.md). Official
firmware matters here: most custom firmwares relax the very checks this
exercises.

What is left is listed in §4. The largest item is the LZRC *encoder*, whose
absence makes archives about a third larger than Sony's rather than wrong.

## 1. What was needed, and what is in hand

The plan this project follows is explicit that reverse engineering comes before
implementation, and that legacy tools are behavioural references rather than
authoritative specifications. That phase is now complete:

| needed | status |
| --- | --- |
| a reference EG `EBOOT.PBP` | **available** — generated by `sign_np`, see §1.2 |
| the NPUMDIMG format | **specified and Sony-checked** — [NPUMDIMG.md](NPUMDIMG.md) |
| BB-MAC, BB-Cipher, fixed-key derivation | **implemented** — `src/npdrm`, verified against a real header |
| ECDSA over KIRK's curve | **implemented** — verifies a real archive's own signature |
| a retail Sony EG `EBOOT.PBP` | **available** — four of them, see §1.1 |
| NPUMDIMG signing keys | **vendored** — and checked to be a real key pair, see §3.5 |
| `sign_np` source | available, builds and runs |
| `ebootsigner` source | not vendored |
| PSPSDK `PrxEncrypter` source | available, but MG-only |
| `libkirk` / PPSSPP KIRK | available via the existing `kirk` module |
| a PSP ISO to test against | **available** — a retail UMD, see [ISO.md](ISO.md) |
| an ISO9660 reader | **implemented**, validated against that disc |

Phase 0 is complete, and the caveat that used to sit here is discharged.

`pspbuild` reads a real UMD without loading it, the format is specified in
[NPUMDIMG.md](NPUMDIMG.md) against real bytes, and that specification has now
been checked against **four genuine Sony Store archives** rather than only
against `sign_np`'s output. Sony's own signatures verify under the published
key, and on the one Sony archive that uses a fixed key the whole chain —
derived version key, header hash, block table, data key and per-block MACs —
recomputes exactly.

The comparison earned its keep. It corrected two things this document and
[NPUMDIMG.md](NPUMDIMG.md) had taken from `sign_np` and stated as facts about
the format: the meaning of `unk_2`, and the `np_flags` value for supplied-key
content. Neither survived contact with a real file. That is the same lesson the
`APE ACADEMY 2` demo taught on the MG path, where a genuine Sony build revealed
two header fields where this crate and Sony legitimately disagree.

What is left is not a caveat about provenance but plain missing work: LZRC
decompression, and assembling a finished archive.

### 1.1 What an EG EBOOT is, and what it is not

This is easy to get wrong — four separate files were mistaken for one during
this work, before four real ones turned up — so it is worth stating precisely.
An EG container has **all** of:

- `PARAM.SFO` with `CATEGORY=EG`
- a non-empty `DATA.PSAR` beginning with the ASCII magic `NPUMDIMG`
- a `DATA.PSP` that is an NPDRM container rather than a `~PSP` PRX

`CATEGORY` is what separates the cases, and there are four in circulation.
All of the following were observed directly:

| CATEGORY | what it is | `DATA.PSP` | `DATA.PSAR` | NPDRM |
| --- | --- | --- | --- | --- |
| `MG` | homebrew, **and every demo** | encrypted PRX | empty | no |
| `UG` | a retail UMD's own `PARAM.SFO` | — (not a PBP) | — | no |
| `EG` | **PSP game bought from the Store** | NPDRM | `NPUMDIMG` | yes |
| `ME` | PSOne classic from the Store | NPDRM | `PSISOIMG0000` | yes |

So the near-misses, and why each one is not EG:

| file | what it actually is |
| --- | --- |
| a downloadable **demo** (`APE ACADEMY 2`, `MotoGP`) | `MG`. Demos shipped as ordinary memory-stick games, never as NPDRM |
| a **firmware update** PBP (`661.PBP`) | `MG`; its `DATA.PSAR` is an update archive, not `NPUMDIMG` |
| a **UMD ISO** | `UG`, and not a PBP at all |
| a **PSOne classic** (`Crash Bandicoot`) | `ME`. Genuinely NPDRM, `KEYS.BIN` and all — but a PS1 disc image, not a UMD image |

The `ME` case is the closest miss and the most instructive: it is a real Store
download with a real 16-byte `KEYS.BIN` version key, so it satisfies "NPDRM
content from PSN" while still being the wrong archive format. **Only a PSP game
takes the EG path.**

`pspbuild inspect` answers it in two lines — `Category` must read `EG` and the
`DATA.PSAR` row must be identified as `NPUMDIMG`.

Four genuine ones are now on hand, and they are worth describing because they
are not what the search had been assuming. All four are Japanese Store
downloads:

| content ID | `np_flags` | key | blocks |
| --- | --- | --- | --- |
| `JP0177-NPJH90121_00-PS3DIVADLCDTC001` | `0x00000003` | supplied | compressed |
| `JP0177-NPJH90213_00-HMPDDT2CA0000000` | `0x00000003` | supplied | compressed |
| `JP0177-NPJH90292_00-HMPDDTEXCA000000` | `0x00000003` | supplied | compressed |
| `JP0082-NPJH90232_00-0000000000000000` | **`0x01000003`** | **fixed** | compressed |

Three carry a content ID ending in a per-title string and use a supplied
version key, which arrives in a `KEYS.BIN` tied to the buying account — those
can be structurally validated and their signatures checked, but not decrypted.

The fourth is the valuable one. `NPJH90232`'s content ID ends in all zeros and
its `np_flags` sets the fixed-key bit, so its version key derives from the ID
alone and the entire chain can be recomputed from the file. A free trial, in
other words, is the fixture that a purchased game could not have been.

### 1.2 Generating one instead of finding one

`sign_np` produces EG EBOOTs from a PSP ISO, and a UMD image is already
available here. That is the route the project plan assumes anyway: §7 and §29
specify differential testing as reference-tool output against candidate output
on the same input.

For deriving a *format* it is arguably better than a single retail file,
because inputs can be varied and the resulting byte movement observed — which
is how per-title values are told apart from constants. One sample can never
show that.

The caveat is worth keeping in view: `sign_np` is a reimplementation, not
Sony's tooling, so agreeing with it proves compatibility with `sign_np` rather
than with Sony. Acceptance by the PSP's own loader still needs a boot test.

## 2. Shape of the pipeline

The overall flow is well attested in public documentation and in the behaviour
of existing tools:

```text
PSP ISO
 └─ ISO9660 reader                extract PSP_GAME assets and EBOOT.BIN   DONE
     └─ NP table                  per-block offsets, sizes, MACs
         └─ block encryption      the ISO in fixed-size encrypted blocks
             └─ NPUMDIMG          header + NP table + encrypted blocks
                 └─ BB-MAC        header authentication
                     └─ ECDSA     signature over the header
                         └─ DATA.PSAR
                             └─ EBOOT.PBP  with DATA.PSP (NPDRM) and CATEGORY=EG
```

The container half is understood — it is an ordinary PBP, documented in
[PBP.md](PBP.md), with `CATEGORY=EG`, an NPDRM `DATA.PSP` and an `NPUMDIMG` in
`DATA.PSAR`. `pspbuild inspect` already identifies all of that:

```console
$ pspbuild inspect EBOOT.PBP
Format:              PBP container
Category:            EG
Sections:
  DATA.PSP     offset 0x0004A1B8       12608 bytes  unrecognised
  DATA.PSAR    offset 0x0004D2F8   612495360 bytes  NPUMDIMG (NPDRM UMD image)
Executable:          EG DATA.PSP is an NPDRM container; not supported yet
```

Everything below that line was where the specification stopped. It no longer
does: the `DATA.PSAR` header is fully understood, and §3 records how.

## 3. The questions this document opened

These were the things that had to be answered with byte-level certainty against
fixtures before any of it could be implemented. All but §3.6 now are, and each
answer is checked against a real archive rather than asserted. They are kept
here with their answers rather than deleted, so the reasoning stays auditable.

### 3.1 NPUMDIMG — **answered**

Header layout, block table, block sizing, MAC and signature coverage are all
specified in [NPUMDIMG.md](NPUMDIMG.md), derived from a reference archive and
reconciled against the real file to the byte.

### 3.2 NP table — **answered and implemented**

0x20 bytes per block: a BB-MAC, an offset, a size, two zeros, then a keyless
self-inverse XOR obfuscation. See [NPUMDIMG.md §5](NPUMDIMG.md).

Implemented in `src/npdrm/table.rs` and validated on Sony's own output: all
6,119 entries of `NPJH90232` decode to a contiguous map of the archive with no
gaps and no overlaps, and its `data_key` — a MAC over the finished table —
recomputes to the value in the header.

### 3.3 Key derivation and tags — **answered**

`version_key` is either supplied or derived from the content ID and
`np_flags`; `header_key` is PRNG; `data_key` is a BB-MAC over the finished
block table. See [NPUMDIMG.md §4](NPUMDIMG.md).

`sceNpDrmGetFixedKey` is now fully specified and implemented — a BB-MAC over
the NUL-padded content ID, then one AES block encryption under a key the low
byte of `np_flags` selects. The KIRK slots behind each step are recorded too:
`0x38` for BB-MAC, `0x39` and `0x63` for BB-Cipher.

The distinction the plan insists on matters most here: `CATEGORY` is a routing
decision, a *tag* is a cryptographic format identifier, and a *key* is the
material itself. They are not interchangeable, and a table conflating them
would be actively misleading. See [KEYS.md](KEYS.md).

### 3.4 BB-MAC and BB-Cipher — **answered and implemented**

Both live in `src/npdrm`, pinned by known-answer tests and verified against a
real archive's header. The question this section asked — whether either is
equivalent to a primitive the crate already had — has a concrete answer:

- **BB-MAC** *is* AES-CMAC under KIRK slot `0x38`, plus at most two block
  encryptions. The crate's existing CMAC is reused directly.
- **BB-Cipher** is **not** the KIRK AES path. It is a counter-mode keystream,
  self-inverse, seeded by the data's own position in the archive.

Type 2 of each is deliberately unimplemented: both route through KIRK command
5, which uses a key derived from the console's fuse ID and does not exist
off-console. NPUMDIMG uses neither. See [NPUMDIMG.md §4.2](NPUMDIMG.md).

### 3.5 ECDSA — **answered and implemented**

Everything this section asked is now settled, and `src/npdrm/ecdsa.rs`
implements it.

**The curve** is KIRK's own 160-bit prime curve, not a published standard,
which is why no general-purpose ECDSA crate could be used and the arithmetic
had to be written here. Full parameters in [NPUMDIMG.md §4.3](NPUMDIMG.md).

**The representations** are the plainest possible: `R` and `S` are 20-byte
big-endian integers concatenated into the 0x28-byte field, and a public key is
its point's `x || y` in the same form.

**The signed bytes** are SHA-1 over header `0x00..0xD8` — *not* the
length-prefixed buffer this section previously recorded. The four leading bytes
in the reference's buffer are a KIRK command header, not part of the message.
See [NPUMDIMG.md §3.2](NPUMDIMG.md).

**The key wrapping is not part of the format.** `sign_np` runs
`encrypt_kirk16_private` over the private key before submitting it, and the
signing command runs `decrypt_kirk16_private` to undo it. Both key off the
console's fuse ID; off-console they cancel exactly, so the signer receives the
plain scalar. `pspbuild` omits the round trip. This section previously said any
reimplementation "has to reproduce that wrapping" — it does not.

The key pair is now **vendored**, with the entry in [KEYS.md §4.3](KEYS.md)
this section asked for, and a test that multiplies the private scalar by the
base point and requires the published public point back.

All of it is verified against a real archive: `tests/npdrm.rs` checks that the
reference EBOOT's own signature validates under the published key, and that the
length-prefixed digest does not.

### 3.6 `DATA.PSP`, PGD, STARTDAT, OPNSSMP

- Which of these are mandatory and which are conditional on content.
- Their structures, as named types rather than one opaque byte array.
- Whether EG `EBOOT.BIN` processing shares anything with MG PRX encryption. It
  must be assumed not to until shown otherwise.

## 4. What remains

Section 3 is answered, the specification has been checked against genuine Sony
archives rather than only against `sign_np` (§1), and the pipeline is built.
`build-eg` on a retail UMD produces a container whose section offsets and total
size are identical to the reference implementation's, with the only differences
being the values the format requires to be random.

What is left:

1. **The LZRC encoder.** Decompression is implemented and validated against
   Sony's own archives; compression is not, so every block is stored raw. The
   archive is valid and reads back correctly, and about a third larger than
   Sony ships. This is a size optimisation, not a correctness gap.
2. **Wider hardware coverage.** One console, one firmware revision, one disc.
   The signature path is measured — a corrupted container is refused on the
   same console, see [COMPATIBILITY.md §1.1](COMPATIBILITY.md) — but nothing
   here is a claim about the PSP line as a whole.
3. **Supplied version keys.** Building is wired for fixed-key titles.
   Supplied-key content needs a `KEYS.BIN` that is tied to the buying account.
4. **`STARTDAT` and `OPNSSMP`** — optional inputs, §3.6, still open.

Not on this list any more: a retail Sony EG EBOOT, which was the standing
blocker for most of this work. Four are now on hand and the comparison has been
made.

### 4.1 What the ISO reader already provides

Available now, and enough to build the input half of the pipeline against:

- `Iso::open` on a retail UMD, with the volume descriptor checked against the
  file's real length.
- `read_file` / `read_optional` for the `PSP_GAME` assets that become PBP
  sections, distinguishing "absent" from "unreadable" — `SND0.AT3` is missing
  from the reference disc, so that distinction is not hypothetical.
- `read_blocks` for raw sectors, which is how the archive will be built.
- Disc identification from `UMD_DATA.BIN`.

What it deliberately does not do is guess at what happens to those sectors next.

## 5. Design commitment

When this is implemented it will be a separate pipeline from MG, not a mode of
it. They share the PBP container and the KIRK primitives and nothing else. The
category check in `Pbp::require_category` exists so that neither can silently
run against the other's container, and that guarantee should survive the EG
implementation rather than being relaxed to accommodate it.
