# NPUMDIMG

The archive an EG `EBOOT.PBP` carries in `DATA.PSAR`: a PSP UMD image cut into
fixed-size blocks, each encrypted and MAC'd, behind a signed 256-byte header.

This was first derived from an archive generated by `sign_np` from a retail
UMD and cross-checked against the `NPUMDIMG_HEADER` declaration in
`sign_np.h`. It has since been **checked against four genuine Sony
Store-downloaded archives**, which corrected two claims and confirmed the
rest — see §7. Where a value is a *rule* it is stated as one; where it is a
constant an implementation happens to write, that is said explicitly, because
those are not the same claim.

**Status: implemented.** The header crypto chain of §3, the block table and
per-block crypto of §5 and §6, and LZRC decompression are all in `src/npdrm`,
and `pspbuild build-eg` writes complete archives. Verified against real
archives, Sony's included: a Sony archive reconstructs block for block into a
UMD image that this crate's own ISO9660 reader parses, and an archive built
from a retail disc matches the reference implementation's for that disc in
every section offset and in total size. Not implemented: the LZRC *encoder*,
so blocks are stored raw. See [EG.md](EG.md).

## 1. Layout

```text
0x000                    NPUMDIMG header          256 bytes
0x100                    block table              iso_blocks * 0x20
0x100 + table_size       encrypted blocks
```

`block_entry_offset` in the header is `0x100`, i.e. the table begins
immediately after the header.

### 1.1 Sizing

```text
block_size = block_basis * 2048            = 32768   (block_basis = 0x10)
iso_blocks = ceil(iso_size / block_size)
table_size = iso_blocks * 0x20
```

Verified against the reference, which reconciles to the byte:

| quantity | value |
| --- | ---: |
| ISO size | 1,136,689,152 |
| `iso_blocks` | 34,689 |
| `table_size` | 1,110,048 |
| `DATA.PSAR` size | 1,137,799,456 |
| `0x100 + table_size + ISO size` | 1,137,799,456 ✓ |

The last identity only holds because the reference was built uncompressed. With
compression the block data is smaller and the total shrinks accordingly; the
header and table sizes are unaffected.

## 2. Header

256 bytes. Offsets are absolute within `DATA.PSAR`.

```text
0x00  u8[8]   magic              "NPUMDIMG"
0x08  u32     np_flags
0x0C  u32     block_basis        0x10
0x10  u8[48]  content_id         ASCII, NUL-padded
0x40  ...     body               96 bytes, ENCRYPTED — see 2.2
0xA0  u8[16]  header_key
0xB0  u8[16]  data_key
0xC0  u8[16]  header_hash        BB-MAC over 0x00..0xC0
0xD0  u8[8]   padding            KIRK PRNG output, not zero
0xD8  u8[40]  ecdsa_sig          over SHA-1 of 0x00..0xD8
```

From the reference archive:

```text
00000000: 4e50 554d 4449 4d47 0300 0001 1000 0000  NPUMDIMG........
00000010: 554c 3030 3030 2d55 4c55 5331 3033 3830  UL0000-ULUS10380
00000020: 5f30 302d 3030 3030 3030 3030 3030 3030  _00-000000000000
00000030: 3030 3030 0000 0000 0000 0000 0000 0000  0000............
00000040: 9db0 b2d3 a44d cf3b 4b62 eca2 6799 c7e0  <- encrypted body
   ...
000000a0: a5d8 5a76 4eb1 e219 ebfb 59dc 33ed 9ceb  <- header_key
000000b0: 2fe5 87e6 b69d 1300 5dd5 d9df 52e7 1478  <- data_key
000000c0: 2aee 4bc0 9335 4984 4122 7a7e fe4d 538d  <- header_hash
000000d0: 6b81 bc9d d4da 8e2b                      <- padding (random)
000000d8: d2a8 4741 ... 6188 edd7                  <- ecdsa_sig
```

The three key/hash fields match what `sign_np` reports for the same run, which
is how the offsets were confirmed rather than assumed.

### 2.1 `np_flags`

Two independent things live in this field:

| bits | meaning |
| --- | --- |
| `0x01000000` | derive the version key from the content ID, rather than expecting a supplied one |
| low byte | which key variant the derivation uses, 0..=3 |

```text
np_flags = 0x01000003               fixed key, variant 3
         = 0x00000003               supplied key, variant 3
```

Observed on genuine Sony archives: three Store downloads carry `0x00000003`
and one carries `0x01000003`. So the low byte is `3` either way, and the only
thing that changes is the fixed-key bit.

`sign_np` writes `0x00000002` when handed a version key, which **disagrees
with Sony's `0x00000003`**. Since the low byte only selects a derivation
variant, and a supplied-key archive derives nothing, it appears not to matter
in practice — but it is a real difference between the reference
implementation and Sony's, and worth knowing about before treating `sign_np`'s
value as canonical.

The flag feeds key derivation (§4), so it is not merely informational.

### 2.2 Body (`0x40..0xA0`)

Encrypted with BB-Cipher, so it is opaque in the file. Field names follow
`sign_np.h`; `unk_N` is a decimal offset within the body.

| offset | field | value written | note |
| --- | --- | --- | --- |
| 0x40 | `sector_size` u16 | `0x0800` | 2048 |
| 0x42 | `unk_2` u16 | `0xE000`, or `0xE001` when the image exceeds 1 GiB | **not** a compression flag — see below |
| 0x44 | `unk_4` u32 | 0 | |
| 0x48 | `unk_8` u32 | `0x1010` | constant, meaning unknown |
| 0x4C | `unk_12` u32 | 0 | |
| 0x50 | `unk_16` u32 | 0 | |
| 0x54 | `lba_start` u32 | 0 | |
| 0x58 | `unk_24` u32 | 0 | |
| 0x5C | `nsectors` u32 | `min(lba_end, 0x6C0BF)` | **clamped** — see below |
| 0x60 | `unk_32` u32 | 0 | |
| 0x64 | `lba_end` u32 | `iso_blocks * block_basis - 1` | 555,023 for the reference |
| 0x68 | `unk_40` u32 | `0x01003FFE` | constant, meaning unknown |
| 0x6C | `block_entry_offset` u32 | `0x100` | where the table starts |
| 0x70 | `disc_id` char[16] | `ULUS-10380` | derived from `content_id`, see below |
| 0x80 | `header_start_offset` u32 | 0 | |
| 0x84 | `unk_68` u32 | 0 | |
| 0x88 | `unk_72` u8 | 0 | |
| 0x89 | `bbmac_param` u8 | 0 | |
| 0x8A | `unk_74` u8 | 0 | |
| 0x8B | `unk_75` u8 | 0 | |
| 0x8C | `unk_76` u32 | 0 | |
| 0x90 | `unk_80` u32 | 0 | |
| 0x94 | `unk_84` u32 | 0 | |
| 0x98 | `unk_88` u32 | 0 | |
| 0x9C | `unk_92` u32 | 0 | |

### 2.3 `nsectors` is clamped, `lba_end` is not

These two fields hold the same expression, but `nsectors` saturates at
`0x6C0BF` — 442,559, or 864 MiB of 2048-byte sectors, a single-layer UMD's
capacity. `lba_end` describes the image; `nsectors` describes the medium the
image claims to sit on, and no real UMD has more sectors than that.

On a disc under 864 MiB the two are equal, which is why this is easy to miss.
The reference archive is 1.08 GiB, so they differ:

| field | value |
| --- | ---: |
| `lba_end` | 555,023 |
| `nsectors` | 442,559 = `0x6C0BF` |

An earlier revision of this document recorded both as the same expression. The
clamp was found by decrypting a real header and checking the fields against
each other rather than against `sign_np.h`.

A Sony archive confirms the other side of the rule: `NPJH90232` is a 191 MiB
image, well under the limit, and there `nsectors == lba_end == 97,903`.

### 2.4 `unk_2` is a size flag, not a compression flag

An earlier revision of this document called `unk_2` "the compression flag",
reading it off a line in `sign_np` that sets `0xE001` in one branch and
`0xE000` in the other. The condition on that branch is `iso_size > 0x40000000`
— a 1 GiB threshold on the *image*, with nothing to do with compression.

A Sony archive settles it directly. `NPJH90232` is compressed — 4,216 of its
6,119 blocks are stored smaller than a full block — and its `unk_2` is
`0xE000`. A compression flag would have to be set there, and is not.

Whether a block is compressed is recorded per block, implicitly, by its size
in the block table (§5). Nothing in the header says the archive as a whole is
compressed.

`disc_id` is rebuilt from the content ID rather than stored independently:
characters 7..11 of `content_id`, a `-`, then characters 11..16. For
`UL0000-ULUS10380_00-...` that yields `ULUS-10380`, matching the disc's own
`UMD_DATA.BIN` (see [ISO.md §5.1](ISO.md)).

Most of this body is zero. Whether the zeros are required or simply what
`sign_np` writes is **not established** — a retail Sony EG EBOOT would settle
it, and none is available.

## 3. Header crypto, in order

The order matters: each step covers the output of the previous one.

1. **Build** the header with `header_key` and `data_key` in place,
   `header_hash` zeroed.
2. **Randomise** `padding` (0xD0, 8 bytes) from the KIRK PRNG.
3. **Encrypt the body**: BB-Cipher over `0x40..0xA0`, **type 1, mode 2**, with
   `header_key` and `version_key`, seed 0.
4. **BB-MAC type 3** over `0x00..0xC0` — which now includes the encrypted body
   and both keys — keyed by `version_key`, written to `header_hash` at 0xC0.
5. **SHA-1** over header bytes `0x00..0xD8`, and nothing else.
6. **ECDSA-sign** that digest with the NPUMDIMG private key, producing 40
   bytes at 0xD8 as `R || S`.

So the signature covers everything before it, the BB-MAC covers everything
before *it*, and the encrypted body is inside both.

**All six steps are implemented and verified against a real archive.**
`tests/npdrm.rs` re-derives the version key from the content ID, recomputes the
BB-MAC over `0x00..0xC0` and gets the `header_hash` already in the file,
decrypts the body to the field values in §2.2, and verifies the ECDSA
signature under the published public key.

### 3.1 The output is not reproducible

`header_key` is KIRK PRNG output, and so is `padding`. Two runs over identical
input therefore differ from `0x40` to the end of the header — confirmed
empirically:

| comparison | bytes that differ |
| --- | --- |
| identical inputs, two runs | `0x40..0xFF` |
| different content ID | `0x12..0x15`, `0x1B..0x1F`, `0x24..0x33`, `0x40..0xFF` |

`0x00..0x0F` never varies, and `content_id` at `0x10..0x40` is plaintext that
tracks the ID exactly.

This is what the project plan anticipated in §7: differential testing has to
compare the *logical* representation, because the raw bytes cannot match. Any
`pspbuild` implementation will need a way to inject a fixed `header_key` and
`padding` for testing, or the comparison is impossible.

### 3.2 The digest is not length-prefixed

Step 5 read differently in an earlier revision: "SHA-1 over a 0xDC-byte buffer,
the little-endian length `0xD8` first, then the header". The reference does
build exactly that buffer — but those four bytes are a **KIRK command header**,
not message data. Command 11 reads a `data_size` from them and hashes only what
follows.

This one is invisible to inspection. Both readings are self-consistent, both
produce a 20-byte digest, and nothing in the header says which is right. The
only thing that can distinguish them is a real signature, and a test now pins
it both ways: the header-only digest verifies, the length-prefixed one does
not.

### 3.3 BB-Cipher's type and mode were transposed

Step 3 read "mode 1, type 2" in an earlier revision, the two parameters read
off the reference's argument list in the wrong order. That mattered more than a
typo would: type 2 derives through KIRK command 5, which uses a key from the
console's fuse ID and cannot be computed off-console at all, and mode 1
*generates* a `header_key` rather than accepting one. Building to the
transposed reading would have produced a pipeline that could not work.

## 4. Keys

| key | size | origin |
| --- | --- | --- |
| `version_key` | 16 | supplied by the caller, or derived by `sceNpDrmGetFixedKey` from `content_id` and `np_flags` |
| `header_key` | 16 | **KIRK PRNG**, fresh per run |
| `data_key` | 16 | BB-MAC over the whole encrypted block table, keyed by `version_key` |
| NPUMDIMG private | 20 | published recovered key, a 160-bit scalar |
| NPUMDIMG public | 40 | two 160-bit coordinates |

`data_key` is a *result*, not an input: it can only be computed after every
block has been encrypted and its table entry filled in. That constrains the
build order — the table must be finalised before the header can be.

### 4.1 The fixed key

`sceNpDrmGetFixedKey` is now **answered**, and implemented in
`src/npdrm/fixed_key.rs`:

```text
key = BB-MAC type 1 over content_id, NUL-padded to 0x30 bytes,
      finalised with NPDRM_FIXED_KEY as the version key
key = AES-ECB(NPDRM_ENC_KEYS[(np_flags & 0xFF) - 1], key)   when the low byte is 1..=3
```

The `0x01000000` bit is what *requests* derivation; the low byte picks which of
three keys performs the final encryption. `NPUMDIMG` uses `0x01000003`, so the
third applies. Since the ID is MAC'd over a fixed 0x30-byte field rather than
over its length, a shorter ID is not a prefix of a longer one — the padding is
part of the message.

The derived key for the reference archive's ID is confirmed against the
reference implementation's own reported value, and then confirmed again by
authenticating the archive's header with it.

### 4.2 What the primitives turned out to be

Both are thinner than their firmware APIs suggest:

- **BB-MAC** is ordinary **AES-CMAC (RFC 4493)** under KIRK slot `0x38`,
  followed by at most two single-block encryptions.
- **BB-Cipher** is a **counter-mode keystream** XORed into the data, and is its
  own inverse. Its seed is a *position* — NPUMDIMG passes each block's byte
  offset over 16 — so every block is keyed to where it sits and cannot be
  relocated without re-encryption.

Both are pinned by known-answer tests at every length their internal buffering
distinguishes. One consequence of testing rather than transliterating: the
reference's `sceDrmBBMacUpdate` **silently discards 16 buffered bytes** when
its pad is exactly full and the next update is at most one block. No archive is
affected, because every NPUMDIMG MAC is computed from a single update, but a
port of the source would have inherited the fault. `pspbuild` does not
reproduce it, and a test records the divergence.

### 4.3 The ECDSA curve — **answered**

KIRK signs on a 160-bit prime curve of Sony's own, not a published standard,
which is why no off-the-shelf ECDSA library applies:

```text
p = FFFFFFFF FFFFFFFF 00000001 FFFFFFFF FFFFFFFF
a = p - 3
b = A68BEDC3 3418029C 1D3CE33B 9A321FCC BB9E0F0B
n = FFFFFFFF FFFFFFFE FFFFB5AE 3C523E63 944F2127
G = (128EC425 6487FD8F DF64E243 7BC0A1F6 D5AFDE2C,
     5958557E B1DB0012 60425524 DBC379D5 AC5F4ADF)
```

Every parameter is checked rather than transcribed: `a` really is `p - 3`, `G`
satisfies the curve equation, `n * G` really is the point at infinity, and the
published private scalar really does generate the published public point. The
signature itself is textbook ECDSA — `R = x(kG)`, `S = (e + Rd)/k mod n` — and
the 0x28-byte field is `R || S`, each 20 bytes big-endian.

The same curve backs KIRK commands 12, 13, 16 and 17. Command 1 uses a
different `b`, `n` and `G` over the same `p`.

### 4.4 The KIRK key wrapping is not part of the format

`sign_np` does not hand the private key to `KIRK_CMD_ECDSA_SIGN` directly. It
concatenates private and public into 0x3C bytes, runs `encrypt_kirk16_private`
over the first 0x20, and passes that; the command then runs
`decrypt_kirk16_private` to get it back.

Both halves key off the console's **fuse ID**, so on hardware this binds a
wrapped key to one machine. Off-console the two are exact inverses under
whatever fuse ID is configured, so the pair cancels and the signer receives the
plain scalar. It is an artifact of the hardware key-loading interface, not of
the signature, and `pspbuild` omits it: reproducing a round trip that provably
changes nothing would only obscure what is signed.

## 5. Block table

One 0x20-byte entry per block, at `0x100`.

```text
0x00  u8[16]  mac       BB-MAC of the encrypted block, keyed by version_key
0x10  u32     offset    absolute offset of the block within DATA.PSAR
0x14  u32     size      encrypted size in bytes
0x18  u32     0
0x1C  u32     0
```

After being filled in, each entry is obfuscated in place:

```c
k0 = p[0]^p[1];  k1 = p[1]^p[2];
k2 = p[0]^p[3];  k3 = p[2]^p[3];
p[4] ^= k3;  p[5] ^= k1;  p[6] ^= k2;  p[7] ^= k0;
```

The four keys derive from the MAC words, and the four XORed words are exactly
`offset`, `size` and the two zeros. It is self-inverse, keyless, and
recoverable from the entry alone — obfuscation rather than encryption.

## 6. Blocks

For each block, in order:

1. Read up to `block_size` bytes of ISO. The final block is short and is
   zero-padded.
2. **Optionally compress** with LZRC. The compressed form is used only if it is
   under `RATIO_LIMIT` = 90% of the original; otherwise the block is stored
   raw. Compressed size is rounded up to 16 bytes.
3. **Encrypt** with BB-Cipher: type 1, mode 2, `header_key`, `version_key`, and
   a seed of `offset >> 4` — the block's byte offset in 16-byte units, so each
   block is keyed to its own position.
4. **BB-MAC type 3** over the encrypted block, keyed by `version_key`, into the
   entry's first 16 bytes.
5. Write, padded up to a 16-byte boundary.

Compression is per block, and an archive freely mixes the two: `NPJH90232`
stores 4,216 of its 6,119 blocks compressed and the remaining 1,903 raw.

**Nothing in the header records whether compression was used.** A block is
compressed exactly when its table entry's `size` is less than `block_size`,
which is the only place the fact is written down. (An earlier revision of this
document attributed that role to `unk_2`; see §2.4 for why that is wrong.)

`pspbuild` implements this section including LZRC decompression. Validated on
`NPJH90232`: all 6,119 blocks decrypt, all 4,216 compressed ones expand to
exactly 32,768 bytes, and the reassembled 191 MiB image parses as an ISO9660
UMD whose `PSP_GAME/PARAM.SFO` names the same title as the archive's content
ID.

The **encoder** is not implemented, and does not need to be. Compression is
per block and optional — a block stored raw is as valid as a compressed one,
and the reference falls back to raw whenever compression saves less than 10%.
An encoder makes archives smaller, not more correct.

## 7. Validated against Sony

The standing caveat in this document used to be that everything here came from
`sign_np`, a reimplementation, so agreeing with it proved compatibility with
`sign_np` rather than with Sony. **That caveat is now discharged.** Four
genuine Store-downloaded EG archives are available, and this crate was run
against them.

What they confirm:

| claim | how it was confirmed |
| --- | --- |
| the ECDSA curve, key and signature encoding | all four archives' signatures **verify under the published public key** |
| the signed range is `0x00..0xD8`, with no length prefix | the same, and the prefixed reading fails |
| the fixed-key derivation | `NPJH90232` uses it; its header authenticates under the derived key |
| BB-MAC, BB-Cipher and the header hash | the same archive's `header_hash` recomputes exactly |
| the block table layout and its obfuscation | 6,119 entries decode to a gapless map with no gaps or overlaps |
| `data_key` is the MAC over the finished table | recomputed and matches the header |
| the per-block MACs | sampled blocks match the MACs their entries carry |

Two documented claims were **wrong** and were corrected by these archives: the
meaning of `unk_2` (§2.4) and the `np_flags` value for supplied-key content
(§2.1). Both came from reading `sign_np`; neither survived contact with a real
file.

Two constants are also now confirmed as Sony's rather than the reference
implementation's invention: `unk_8` = `0x1010` and `unk_40` = `0x01003FFE`
appear identically in Sony's archives. Their *meaning* is still unknown.

## 8. What is still not established

- Whether the zeroed body fields are required or merely conventional.
- What `unk_8` = `0x1010` and `unk_40` = `0x01003FFE` mean.
- **The LZRC encoder.** Decompression is implemented and validated against
  Sony's own archives; compression is not. Archives can therefore be read but
  would have to be written with every block stored raw, which is valid and
  merely larger.
- **Supplied version keys.** Three of the four Sony archives use them. The key
  ships separately, in a `KEYS.BIN` tied to the account that bought the
  content, so those archives can be structurally validated and their
  signatures checked, but not decrypted.
- Building a complete archive. The header is implemented and the block layer
  is implemented; assembling them into a finished `DATA.PSAR` is not.
- `STARTDAT` and `OPNSSMP`, both optional inputs, are not covered here.

Acceptance by the PSP's loader remains a separate claim from format
correctness, and still needs a boot test — see
[COMPATIBILITY.md](COMPATIBILITY.md) for how the MG path was settled that way.
