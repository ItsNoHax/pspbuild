# NPUMDIMG

The archive an EG `EBOOT.PBP` carries in `DATA.PSAR`: a PSP UMD image cut into
fixed-size blocks, each encrypted and MAC'd, behind a signed 256-byte header.

Everything here was derived from a reference archive generated by `sign_np`
from a retail UMD, cross-checked against the `NPUMDIMG_HEADER` declaration in
`sign_np.h`, and confirmed by differential runs. Where a value is a *rule* it
is stated as one; where it is a constant `sign_np` happens to write, that is
said explicitly, because those are not the same claim.

**Status: specification only.** Nothing here is implemented yet. See
[EG.md](EG.md).

## 1. Layout

```text
0x000                    NPUMDIMG header          256 bytes
0x100                    block table              iso_blocks * 0x20
0x100 + table_size       encrypted blocks
```

`block_entry_offset` in the header is `0x100`, i.e. the table begins
immediately after the header.

### 1.1 Sizing

```text
block_size = block_basis * 2048            = 32768   (block_basis = 0x10)
iso_blocks = ceil(iso_size / block_size)
table_size = iso_blocks * 0x20
```

Verified against the reference, which reconciles to the byte:

| quantity | value |
| --- | ---: |
| ISO size | 1,136,689,152 |
| `iso_blocks` | 34,689 |
| `table_size` | 1,110,048 |
| `DATA.PSAR` size | 1,137,799,456 |
| `0x100 + table_size + ISO size` | 1,137,799,456 ✓ |

The last identity only holds because the reference was built uncompressed. With
compression the block data is smaller and the total shrinks accordingly; the
header and table sizes are unaffected.

## 2. Header

256 bytes. Offsets are absolute within `DATA.PSAR`.

```text
0x00  u8[8]   magic              "NPUMDIMG"
0x08  u32     np_flags
0x0C  u32     block_basis        0x10
0x10  u8[48]  content_id         ASCII, NUL-padded
0x40  ...     body               96 bytes, ENCRYPTED — see 2.2
0xA0  u8[16]  header_key
0xB0  u8[16]  data_key
0xC0  u8[16]  header_hash        BB-MAC over 0x00..0xC0
0xD0  u8[8]   padding            KIRK PRNG output, not zero
0xD8  u8[40]  ecdsa_sig          over SHA-1 of 0x00..0xD8
```

From the reference archive:

```text
00000000: 4e50 554d 4449 4d47 0300 0001 1000 0000  NPUMDIMG........
00000010: 554c 3030 3030 2d55 4c55 5331 3033 3830  UL0000-ULUS10380
00000020: 5f30 302d 3030 3030 3030 3030 3030 3030  _00-000000000000
00000030: 3030 3030 0000 0000 0000 0000 0000 0000  0000............
00000040: 9db0 b2d3 a44d cf3b 4b62 eca2 6799 c7e0  <- encrypted body
   ...
000000a0: a5d8 5a76 4eb1 e219 ebfb 59dc 33ed 9ceb  <- header_key
000000b0: 2fe5 87e6 b69d 1300 5dd5 d9df 52e7 1478  <- data_key
000000c0: 2aee 4bc0 9335 4984 4122 7a7e fe4d 538d  <- header_hash
000000d0: 6b81 bc9d d4da 8e2b                      <- padding (random)
000000d8: d2a8 4741 ... 6188 edd7                  <- ecdsa_sig
```

The three key/hash fields match what `sign_np` reports for the same run, which
is how the offsets were confirmed rather than assumed.

### 2.1 `np_flags`

```text
np_flags = 0x00000002               when a version key is supplied
         = 0x01000003               when using the derived fixed key
```

The reference used the fixed key, hence `0x01000003`. The flag feeds key
derivation (§4), so it is not merely informational.

### 2.2 Body (`0x40..0xA0`)

Encrypted with BB-Cipher, so it is opaque in the file. Field names follow
`sign_np.h`; `unk_N` is a decimal offset within the body.

| offset | field | value written | note |
| --- | --- | --- | --- |
| 0x40 | `sector_size` u16 | `0x0800` | 2048 |
| 0x42 | `unk_2` u16 | `0xE000`, or `0xE001` compressed | the compression flag |
| 0x44 | `unk_4` u32 | 0 | |
| 0x48 | `unk_8` u32 | `0x1010` | constant, meaning unknown |
| 0x4C | `unk_12` u32 | 0 | |
| 0x50 | `unk_16` u32 | 0 | |
| 0x54 | `lba_start` u32 | 0 | |
| 0x58 | `unk_24` u32 | 0 | |
| 0x5C | `nsectors` u32 | `iso_blocks * block_basis - 1` | |
| 0x60 | `unk_32` u32 | 0 | |
| 0x64 | `lba_end` u32 | `iso_blocks * block_basis - 1` | 555,023 for the reference |
| 0x68 | `unk_40` u32 | `0x01003FFE` | constant, meaning unknown |
| 0x6C | `block_entry_offset` u32 | `0x100` | where the table starts |
| 0x70 | `disc_id` char[16] | `ULUS-10380` | derived from `content_id`, see below |
| 0x80 | `header_start_offset` u32 | 0 | |
| 0x84 | `unk_68` u32 | 0 | |
| 0x88 | `unk_72` u8 | 0 | |
| 0x89 | `bbmac_param` u8 | 0 | |
| 0x8A | `unk_74` u8 | 0 | |
| 0x8B | `unk_75` u8 | 0 | |
| 0x8C | `unk_76` u32 | 0 | |
| 0x90 | `unk_80` u32 | 0 | |
| 0x94 | `unk_84` u32 | 0 | |
| 0x98 | `unk_88` u32 | 0 | |
| 0x9C | `unk_92` u32 | 0 | |

`disc_id` is rebuilt from the content ID rather than stored independently:
characters 7..11 of `content_id`, a `-`, then characters 11..16. For
`UL0000-ULUS10380_00-...` that yields `ULUS-10380`, matching the disc's own
`UMD_DATA.BIN` (see [ISO.md §5.1](ISO.md)).

Most of this body is zero. Whether the zeros are required or simply what
`sign_np` writes is **not established** — a retail Sony EG EBOOT would settle
it, and none is available.

## 3. Header crypto, in order

The order matters: each step covers the output of the previous one.

1. **Build** the header with `header_key` and `data_key` in place,
   `header_hash` zeroed.
2. **Randomise** `padding` (0xD0, 8 bytes) from the KIRK PRNG.
3. **Encrypt the body**: BB-Cipher over `0x40..0xA0`, with mode 1, type 2,
   `header_key` and `version_key`, seed 0.
4. **BB-MAC** over `0x00..0xC0` — which now includes the encrypted body and
   both keys — keyed by `version_key`, written to `header_hash` at 0xC0.
5. **SHA-1** over a 0xDC-byte buffer: the little-endian length `0xD8` in the
   first four bytes, then header bytes `0x00..0xD8`.
6. **ECDSA-sign** that digest with the NPUMDIMG private key, producing 40
   bytes at 0xD8.

So the signature covers everything before it, the BB-MAC covers everything
before *it*, and the encrypted body is inside both.

### 3.1 The output is not reproducible

`header_key` is KIRK PRNG output, and so is `padding`. Two runs over identical
input therefore differ from `0x40` to the end of the header — confirmed
empirically:

| comparison | bytes that differ |
| --- | --- |
| identical inputs, two runs | `0x40..0xFF` |
| different content ID | `0x12..0x15`, `0x1B..0x1F`, `0x24..0x33`, `0x40..0xFF` |

`0x00..0x0F` never varies, and `content_id` at `0x10..0x40` is plaintext that
tracks the ID exactly.

This is what the project plan anticipated in §7: differential testing has to
compare the *logical* representation, because the raw bytes cannot match. Any
`pspbuild` implementation will need a way to inject a fixed `header_key` and
`padding` for testing, or the comparison is impossible.

## 4. Keys

| key | size | origin |
| --- | --- | --- |
| `version_key` | 16 | supplied by the caller, or derived by `sceNpDrmGetFixedKey` from `content_id` and `np_flags` |
| `header_key` | 16 | **KIRK PRNG**, fresh per run |
| `data_key` | 16 | BB-MAC over the whole encrypted block table, keyed by `version_key` |
| NPUMDIMG private | 20 | published recovered key, a 160-bit scalar |
| NPUMDIMG public | 40 | two 160-bit coordinates |

`data_key` is a *result*, not an input: it can only be computed after every
block has been encrypted and its table entry filled in. That constrains the
build order — the table must be finalised before the header can be.

The ECDSA key pair is not used raw. `sign_np` concatenates private and public
into a 0x3C-byte pair, passes it through `encrypt_kirk16_private`, and hands
the 0x20-byte result plus the 0x14-byte digest to `KIRK_CMD_ECDSA_SIGN`.

## 5. Block table

One 0x20-byte entry per block, at `0x100`.

```text
0x00  u8[16]  mac       BB-MAC of the encrypted block, keyed by version_key
0x10  u32     offset    absolute offset of the block within DATA.PSAR
0x14  u32     size      encrypted size in bytes
0x18  u32     0
0x1C  u32     0
```

After being filled in, each entry is obfuscated in place:

```c
k0 = p[0]^p[1];  k1 = p[1]^p[2];
k2 = p[0]^p[3];  k3 = p[2]^p[3];
p[4] ^= k3;  p[5] ^= k1;  p[6] ^= k2;  p[7] ^= k0;
```

The four keys derive from the MAC words, and the four XORed words are exactly
`offset`, `size` and the two zeros. It is self-inverse, keyless, and
recoverable from the entry alone — obfuscation rather than encryption.

## 6. Blocks

For each block, in order:

1. Read up to `block_size` bytes of ISO. The final block is short and is
   zero-padded.
2. **Optionally compress** with LZRC. The compressed form is used only if it is
   under `RATIO_LIMIT` = 90% of the original; otherwise the block is stored
   raw. Compressed size is rounded up to 16 bytes.
3. **Encrypt** with BB-Cipher: mode 1, type 2, `header_key`, `version_key`, and
   a seed of `offset >> 4` — the block's byte offset in 16-byte units, so each
   block is keyed to its own position.
4. **BB-MAC** the encrypted block, keyed by `version_key`, into the entry's
   first 16 bytes.
5. Write, padded up to a 16-byte boundary.

Compression is per block: an archive can mix compressed and raw blocks, and
`unk_2` records only that compression was enabled at all.

## 7. What is not yet established

- Whether the zeroed body fields are required or merely conventional.
- What `unk_8` = `0x1010` and `unk_40` = `0x01003FFE` mean.
- Whether a retail Sony EG EBOOT agrees with all of the above. Every statement
  here is derived from `sign_np`'s behaviour, so it describes what `sign_np`
  produces and what the PSP is known to accept from it — not necessarily what
  Sony's own tooling emits.
- `STARTDAT` and `OPNSSMP`, both optional inputs, are not covered here.

That last point is the important caveat. `sign_np` is a reimplementation, and
agreeing with it proves compatibility with `sign_np`. Acceptance by the PSP's
loader is a separate claim that needs a boot test — see
[COMPATIBILITY.md](COMPATIBILITY.md) for how the MG path was settled the same
way.
